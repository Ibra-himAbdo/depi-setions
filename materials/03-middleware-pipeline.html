Middleware

حاجة بتقف في نص الطريق بين الـ Request اللي جاي والـ Response اللي راجع. وكل Request بيعدّي على سلسلة منها بالترتيب.

تكمّلبتنادي await next() وتسلّم الطلب للـ Middleware اللي بعدها.
توقّفبترد بنفسها من غير next()، والطلب عمره ما يوصل للـ endpoint. اسمها short-circuit.
تلفّ حوالين الباقيبتشتغل قبل next وبعده. زي الـ logging وحماية الـ Exception.

ليه AuthN قبل AuthZ؟

تخيّل مبنى فيه بوابة أمن وبعدها غرفة عليها حارس. الأمن عند البوابة بيشوف بطاقتك الأول. وبعدين حارس الغرفة بيبص على اللي الأمن سجّله ويقرر تدخل ولا لأ.

AuthN

Authentication · إنت مين؟ بتتأكد من هويتك (توكن أو كوكي) وتكتبها في HttpContext.User. زي الأمن اللي بيشوف بطاقتك عند البوابة.

AuthZ

Authorization · مسموحلك؟ بتقرا HttpContext.User (الـ Role والـ Claims) وتقرر تدخّلك ولا لأ. زي حارس الغرفة اللي بيشوف التصريح.

AuthZ بتقرا اللي AuthN كتبته. لو AuthZ اشتغلت الأول، هتلاقي User لسه فاضي.

401 ولا 403؟

الاتنين رفض، بس معناهم مختلف. وده بيوضّح ليه الترتيب المعكوس بيدّي رد مضلّل.

401

مش عارفك اسمها Unauthorized بس معناها Unauthenticated. الطلب جه من غير هوية سليمة. الحل إنك تسجّل دخول. بتطلع من Challenge.

403

عارفك بس مش مسموحلك الهوية سليمة لكن الصلاحية ناقصة. تسجيل الدخول تاني مش هيفيد. بتطلع من Forbid.

والـ MVC فين من ده كله؟

الـ MVC هو الـ endpoint اللي في آخر الـ pipeline. الـ Middlewares بتخلّص شغلها الأول، وبعدين MapControllers() بيسلّم الطلب لـ MVC. وله pipeline صغير جواه خاص بيه اسمه الـ Filters.

Modelالبيانات وقواعدها: الـ classes وقاعدة البيانات والتحقق (validation).
Viewاللي المستخدم بيشوفه: صفحة HTML بـ Razor، أو JSON لو API.
Controllerبيستقبل الطلب، بيكلّم الـ Model، ويختار الـ View أو الرد. هو الـ endpoint في الـ pipeline.

Middleware ولا Filter؟

Middleware

  • بتشوف كل الطلبات، حتى الصور والـ CSS والـ API.
  • متعرفش حاجة عن MVC (الـ Action أو الـ ModelState).
  • بتتحط في Program.cs.
  • مثال: HTTPS وCORS وAuth وLogging.

Filter

  • بتشتغل بس لما MVC يكون هو الـ endpoint.
  • بتعرف الـ Action والـ ModelState والنتيجة.
  • بتتحط على Controller أو Action، أو على الكل.
  • مثال: التحقق من ModelState وتغليف الرد وتحويل Exception لرد.

لو الشغل يخص كل الطلبات: Middleware. ولو يخص الـ Actions بس ومحتاج تعرف الـ Action أو الـ ModelState: Filter.

وفيه رابط بين الاتنين. UseRouting بتحدد الـ Action الأول وتحمل بياناته (زي [Authorize])، وبعدين UseAuthorization بتقراها. عشان كده Routing قبل Authorization.

الترتيب اللي بتكتبه في Program.cs

الترتيب ده مش عشوائي. كل واحدة في مكانها لسبب. الاتنين اللي حواليهم إطار هما موضوعنا.

  1. app.UseExceptionHandler("/error");في الأول، عشان تمسك أي Exception بتحصل في أي Middleware بعدها.
  2. app.UseHsts(); app.UseHttpsRedirection();قبل ما أي بيانات حساسة (توكن، كوكي) تتبعت على اتصال مش مشفّر.
  3. app.UseStaticFiles();بترد على الصور والـ CSS بدري وتوقّف الطلب، فمفيش داعي يعدّي على Auth.
  4. app.UseRouting();بتحدد الـ endpoint، عشان اللي بعدها يقرا بياناته (زي [Authorize]). في minimal hosting بتتضاف لوحدها.
  5. app.UseCors();بعد Routing وقبل Auth، عشان طلبات الـ preflight متتحسبش مرفوضة.
  6. app.UseAuthentication();إنت مين؟ بتملا HttpContext.User. لازم تسبق أي حد محتاج يعرف الهوية.
  7. app.UseAuthorization();مسموحلك؟ بتقرا User وبيانات الـ endpoint وتقرر.
  8. app.MapControllers();الـ endpoints نفسها. هنا بيبدأ الـ MVC بـ pipeline الـ Filters بتاعه، بعد ما كل اللي قبله عدّى.

الـ Middleware اللي بتكتبها بنفسك مكانها حسب شغلتها. لو عايزة تشوف كل الطلبات حتى المرفوضة، حطها في الأول. ولو محتاجة تعرف المستخدم، حطها بعد UseAuthentication.

الخلاصة

AuthN بتعرف إنت مين. AuthZ بتقرر تعمل إيه. ولازم تعرف الأول عشان تقرر.

next
بتسلّم الطلب للـ Middleware اللي بعدها، وبترجع لما الباقي يخلص.
short-circuit
تردّ من غير next، فالباقي مبيشتغلش.
HttpContext.User
الهوية الحالية. AuthN بتكتبها، وAuthZ بتقراها.
Filter
زي الـ Middleware بس جوه MVC، وبتلفّ حوالين الـ Action.
401 / 403
مش عارفك / عارفك بس مش مسموحلك.
