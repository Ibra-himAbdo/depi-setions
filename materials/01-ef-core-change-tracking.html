قواعد تمشي عليها

كل واحدة منهم طلعت من حاجة جربتها فوق.

  1. .AsNoTracking()مناسب غالبًا للقراءات فقط (قوائم وتقارير)، وبيقلّل تكلفة التتبّع. الأداء الفعلي يتأثر بنمط الاستعلام.
  2. p.Price = 500; await db.SaveChangesAsync();الـ entity متتبّعة؟ عدّل واحفظ. مش محتاج Update.
  3. db.Products.Update(fromApi);للـ entity غير المتتبّعة بعد تحويل بيانات الـ DTO إلى Entity. غالبًا بيعلّم الخصائص Modified؛ خليك واعي لتحديث الأعمدة غير المقصودة وتعارض النسخ.
  4. Remove(p) / ExecuteDeleteAsync()الأولى بتحدد حالة الـ entity وتتنفّذ عند SaveChanges. التانية بتنفّذ DELETE مباشرة بدون تحميل الـ entities أو تتبّعها.
  5. Add(p)دايمًا تقريبًا. AddAsync بس لو الـ key generator بيكلّم الـ DB (زي HiLo). وده نادر.
  6. services.AddDbContext<AppDb>()في تطبيقات الويب غالبًا بيتسجّل Scoped لكل Request. تجنّب إطالة عمره بلا داعٍ لأن التتبّع بيستهلك ذاكرة.

الخلاصة

معظم تغييرات الحالة بتحصل في الذاكرة. الـ SQL بيتنفّذ وقت الحفظ أو الاستعلام، مع استثناءات مهمة زي مولّدات المفاتيح وبعض عمليات ExecuteUpdate/Delete.

Change Tracker
داخل الـ DbContext؛ بيتابع الـ entities المتتبّعة وحالتها.
EntityState
Detached / Unchanged / Added / Modified / Deleted.
Snapshot
القيم الأصلية اللي بيستخدمها تتبّع الـ Snapshot الافتراضي لاكتشاف الاختلاف.
AsNoTracking
قراءة بلا تتبّع افتراضي؛ التعديلات مش هتتحفظ تلقائيًا بدون Attach أو Update.
AddAsync
لحالة الـ key generator اللي بيكلّم الـ DB. مش بتحفظ في الـ DB.
